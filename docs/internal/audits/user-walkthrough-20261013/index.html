Five reproduced problems and their recovery behavior

Failure and timing captures use deliberate local browser HTTP 503 or delay injection. They demonstrate the named UI behavior under those conditions.

WALK-01 · Search exposes results from the previous query

Manually observed locally

Before / problem: Changing the query retained old clickable results during the debounce window; an earlier in-flight response could replace results for the new text.

After / change: Abort the old request immediately, clear its results, and accept responses only for the current query.

Observed result: With a manually delayed local response, changing the query immediately removed the old results and showed the pending search.

Manual reproduction: Browser response delay.

WALK-02 · Failed chat rename loses the entered name

Manually observed locally

Before / problem: A rejected Rename discarded the typed title and switched away from the Rename dialog.

After / change: Retain the Rename action and typed title after a failure, show its error, and allow an explicit retry.

Observed result: A manually injected local HTTP 503 retained the name. Retrying Rename succeeded with that name.

Manual reproduction: Browser HTTP 503 interception.

WALK-03 · Stop fails silently during a running response

Manually observed locally

Before / problem: A failed Stop request left the response running without explaining the failure.

After / change: Show a Stop-specific failure beside the composer and restore the Stop action for retry.

Observed result: A manually injected local HTTP 503 showed a visible Stop-specific alert during a running response. Retrying Stop succeeded and the running-response controls disappeared. No page errors were observed in that recovery flow.

Manual reproduction: Browser HTTP 503 interception; deterministic local AI response.

WALK-04 · Failed saved-query operation leaves Saving stuck

Manually observed locally

Before / problem: A failed Save left the pending label and disabled controls without a useful recovery path.

After / change: Show the transport failure, retain the query draft and the original operation identity, and allow an explicit retry when the outcome is unknown.

Observed result: A manually injected local HTTP 503 preserved the draft and exposed retry. Retrying the same operation succeeded without an extra copy.

Manual reproduction: Browser HTTP 503 interception.

WALK-05 · Enter submits raw @context text while lookup is pending

Manually observed locally after the final context change

Before / problem: Pressing Enter during a pending context lookup sent the raw @query as a chat message instead of waiting for context selection.

After / change: Separate the browser’s pending lookup request from server-returned search results. Enter waits while lookup is pending; a failed current request offers Retry search, which retries that context query.

Observed result: Enter during a delayed context lookup retained the draft and made no chat-turn request. A manually injected local HTTP 503 exposed Retry search; retry returned permitted dashboard and semantic-model options. Selecting a permitted semantic model added its context chip.

Manual reproduction: Browser response delay and HTTP 503 interception.

Two source hardenings with limited runtime evidence

HARD-01 · Favorites and Last opened belong to the signed-in principal

Source hardening; limited local observation

Before / problem: Browser-wide preference keys could attribute one account’s favorites and recents to another account.

After / change: Catalog and dashboard report use the same canonical-principal-scoped favorite key; recents are scoped as well. Legacy keys remain untouched but unused because their owner is unknown.

Observed result: A scoped browser storage key and the current account’s Favorites view were observed. A two-account walkthrough in the same browser was not obtained.

Migration: One-time Favorites and Last opened reset; no legacy ownership is inferred.

HARD-02 · Saved-query mutation controls use current server capabilities

Source hardening; owner path observed; nonowner path unverified

Before / problem: Shared saved-query controls must not infer mutation authority from visibility or a role label.

After / change: Project canEdit and canArchive through the same lifecycle authorizer as mutations. The UI shows Save changes and Archive only for the permitted current actor. Server mutations still independently reauthorize.

Observed result: The valid owner retained Save changes, Duplicate and Archive, and owner save/archive actions worked. The nonowner flow was not exercised in this password-login audit.
