# LeapView v0.4.0-alpha.1 — Explorer, governed credentials and authoring recovery

This alpha expands saved explorations, connects assistant results to Explorer
and Search, improves dashboard tables and charts, and introduces typed access
and administrator-managed credential workflows. It includes the changes since
`v0.3.0-alpha.1` and remains intended for controlled evaluation and feedback.

**Read the upgrade requirements before using existing state.** This is an alpha
with incompatible credential and command changes, not a promise of production
readiness or stable interfaces.

## Highlights

### Explore, save and follow assistant results

- Save canonical explorations, share and export them under governed access, and
  carry results into dashboards. Explorer retains filters, result controls and
  navigation context.
- Open assistant charts in Explorer and assistant searches in Search. Browser
  history, embedded Explorer context and reconnect state are preserved.
- Explorer agent integration retains chat drafts and context across reconnects.
  Monthly exploration saves normalize the optional empty time alias without
  relaxing authored-query validation. Successful preview retries clear their
  previous error.

### Build and read dashboards more reliably

- Tables support hierarchy, image cells and content-fit sizing. Follow-up fixes
  improve sort announcements, focused controls and Escape handling.
- Charts preserve narrow category endpoints and fit responsive legends; map
  disclosures and controls remain usable in short frames.
- Builder and Explorer agent workflows retain active prompts, distinguish
  stale table reads from write failures, and recover chat and preview state.
  Saved chat visuals and scoped chart Add/Remove actions improve dashboard
  handoff.

### Govern access and connection credentials

- Typed action/resource permissions, durable grants and role/token
  administration make delegated authority explicit. SCIM deactivation revokes
  sessions and memberships.
- Role assignments approved by an authorized access manager take effect on the
  next request without republishing the project. Unapproved additions remain
  staged. Admin account and session views distinguish blocked users, expired
  sessions and recorded activity, with improved keyboard and mobile controls.
- Browser settings for session and personal API-token management require
  platform administration. Non-admin storage pages show authorized catalog
  metadata, and Explorer and dashboard action controls follow effective resource
  permissions.
- SSO stays opt-in. With the instance stopped, `leapview admin nominate-sso-admin`
  previews nomination of an existing OIDC user by exact instance and principal
  IDs; `--apply` records the administrator assignment. Follow the
  [OIDC setup procedure](https://leapview.dev/docs/security/oidc) for cutover.
- Established chat streams recheck credentials before sending data or idle
  keepalives. Revoked or expired credentials, blocked accounts and unavailable
  authorization state stop further delivery.
- Administrator-managed credentials support encrypted drafts, validation,
  activation, key rewrapping, restart recovery, first-source onboarding and
  dependency-aware retirement. These workflows require explicit customer
  ownership and an instance-bound keyring.
- Pipeline run investigation and manual refresh preserve caller authorization
  across deferred execution.

### Author locally and recover interrupted work

- CLI root discovery works offline; local and remote `doctor` checks are
  read-only. Command discovery and noninteractive errors are more explicit.
- Local authoring startup, restart and invalid-edit recovery retain the last
  usable project state.
- Fresh host `leapviewctl activate-first-install` waits for Docker health to
  recover after publication, then rechecks application readiness before
  applying the public proxy configuration.
- Runtime fixes cover authenticated semantic Arrow streaming, reader draining
  and snapshot lease readiness. Managed-data uploads can recover multipart
  completion while independent cleanup remains fenced.

## Compatibility and upgrade requirements

1. **Start from the actual published predecessor.** `v0.3.0-alpha.1` is revision
   `bf792c45bd1bf346ab30d33c467ad43f802359b4`, image
   `ghcr.io/flidai/leapview@sha256:f435b922968975c295ae738e622805c4c738b9cdf6b7624a4cd5cd7af0557a86`,
   at control schema 28. This candidate contains schema 67, with forward
   migrations 029–067. A schema-32 development fixture does not establish an
   upgrade from the published alpha. Rehearse against restored state and retain
   recovery material before changing an installation.
2. **Replace legacy API tokens.** Migrations 034 and 040 revoke legacy tokens.
   Prepare typed replacement credentials with explicit action/resource
   permissions and verify retained viewer grants and independent publisher and
   reviewer authority. Existing bearer tokens must not be expected to survive.
   Browser management of personal API tokens and sessions requires a platform
   administrator; review workflows that used these settings as a non-admin.
3. **Configure credential ownership and keys explicitly.** The new store needs
   a private instance-bound `LEAPVIEW_CREDENTIAL_KEYRING_FILE` and customer
   ownership setup. `LEAPVIEW_AGENT_CREDENTIAL_KEY` does not enable the new
   store or decrypt its rows; there is no automatic legacy ciphertext import.
   Preserve existing state and keys. The published schema-28 deployment-owned
   agent settings are distinct from later database-managed encrypted revisions.
4. **Update command invocations and validate authored resources.** Use
   `leapview serve` to start the server; bare `leapview` displays help. Use
   command-supported `--format json` and check the candidate's command help.
   Connections, sources, models, semantic models and pipelines require resource
   envelopes; dashboard fragments remain supported. Validate projects with the
   candidate CLI before activation.
5. **Use the recovery procedure qualified for the installation.** The bounded
   Linux `leapviewctl host upgrade` path requires a private qualified request,
   prepared rehearsal, immutable PostgreSQL 18, and the exact four local
   volumes for PostgreSQL, instance state, Caddy data and Caddy configuration.
   Journal-driven recovery before commit restores the paired predecessor state.
   It is not a general downgrade of a completed upgrade. External PostgreSQL,
   remote object stores and other layouts need separate recovery qualification.
6. **Review role approval behavior.** Migration 067 records administrator
   approval of typed role assignments. Existing rows default to unapproved;
   published role authority is preserved and staged assignments are not
   retroactively approved. Its down migration is intentionally rejected.
   Retain paired recovery state rather than assuming a schema downgrade is
   available.

Read the [upgrade guide](https://leapview.dev/docs/guides/operate/upgrades) and
[backup and restore guide](https://leapview.dev/docs/guides/operate/backup-restore).
Publishing a release does not deploy or upgrade an existing installation.

## Distribution and qualification scope

- The conventional server image targets Linux AMD64 and ARM64. Compose
  operations and authoring CLI archives target Linux/macOS on AMD64/ARM64.
- Publication requires exact-archive native Linux authoring lifecycle checks;
  macOS archive checks are static. Do not infer macOS lifecycle or browser
  preview timing acceptance from those checks.
- The release workflow requires exact published-alpha upgrade and paired-state
  recovery evidence before publication. The bounded fixture does not prove the
  complete operator-host procedure or every external PostgreSQL/object-store
  topology.
- Conventional Compose acceptance uses the original release bundles on the
  supported Ubuntu/Debian guest matrix, with bundled/external PostgreSQL.
  Nix outputs and managed production deployment retain separate acceptance.
- Desktop downloads remain withdrawn. This server/CLI alpha does not restore
  Desktop availability or adopt the reverted deployment architecture proposal.

These notes describe the intended alpha scope. They do not certify a candidate
that has not passed qualification. Use the publishing workflow's actual
revision, immutable image digest, archive checksums and retained qualification
reports for the released artifacts. Public-download installation and Linux CLI
lifecycle acceptance must also pass before availability is announced.

production availability SLA is claimed. External AI answer quality remains
provider-dependent. The limitations here are not an exhaustive bug inventory.
